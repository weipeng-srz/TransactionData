## 一条可长期保留的上下文应包含

- **事实和边界**：现在的行为是什么，适用哪类市场/账户/数据，哪些情况不可用。
- **定位信息**：仓库相对路径、关键符号及测试文件；优先链接与符号，避免易漂移的行号。
- **验证证据**：测试或复现方法。结果型报告额外写明日期、版本/提交、样本和限制。
- **同步关系**：相关数据契约、专题与地图的链接。公共规则只保留一处正文，其余引用。

已有专题写最终实现，历史报告保留当时事实；不把未完成计划写成已实现功能，不把旧报告中的指标写成当前保证。

## 交付前检查

1. 沿代码差异逐项匹配上表。新文件与新功能必须能从 AI 入口经地图到达。
2. 检查 Markdown 相对链接、源码路径、符号和命令确实存在；更新标题后检查锚点；移除陈旧引用。
3. 运行 [验证指南](verification.md) 中适用检查，记录实际结果和未验证范围；纯文档改动无需重跑业务回测。
4. 检查 `git diff --check`、`git diff --stat` 与 `git status --short`，确认新增文档未被忽略，没有混入生成数据或凭据。
5. 提交前按根指南执行 GitNexus `detect_changes()`；回归评审使用相对 `main` 的 compare。图谱结果不能代替 Git 对新增、未跟踪文档的检查。
6. 交付说明包含：行为变化、更新文档、已执行验证、未验证事项；无需更新某项文档时说明理由。

GitNexus 管理的 `<!-- gitnexus:start -->` / `<!-- gitnexus:end -->` 区域可由索引工具刷新。手写规则置于区外；刷新后核对 `AGENTS.md` 和 `CLAUDE.md`，不要用生成内容覆盖人工维护的任务入口。
